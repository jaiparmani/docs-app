# Why Retries Make Outages Worse

<small>6 min read</small>

The instinct behind a retry is almost too obvious to question: a request failed, probably because of some transient hiccup, so try it again. It's the same logic behind jiggling a key in a stubborn lock. Most engineers add retry logic to a client without thinking of it as a design decision at all — it feels more like basic hygiene, the kind of thing you'd feel embarrassed not to have. And yet naive retry logic is one of the most common ways a small, recoverable problem turns into a large, sustained one, to the point where a meaningful fraction of the worst outages at large internet companies have "retries" somewhere in the postmortem, not as the original cause, but as the thing that took a minor blip and turned it into an hours-long recovery.

The question people don't think to ask is: what happens when everyone retries at once?

## Synchronization is the hidden cost

Picture a service with ten thousand active clients, all issuing requests roughly continuously. The service briefly stumbles — a deploy, a garbage collection pause, a brief spike in load, doesn't matter what — and for a couple of seconds, requests start timing out. Every client that was waiting on a request at that moment sees a failure at roughly the same time, because they were all talking to the same struggling service during the same narrow window. If every one of those clients is running the same simple logic — on failure, wait a fixed short interval, then retry — then a few seconds later, all ten thousand of them retry at once. Not because they coordinated. Because they were all victims of the same outage at the same moment, running identical logic, so their independent decisions happen to land in the same instant.

This is the thundering herd: a population of independent clients, synchronized entirely by accident, converging on the same server at the same moment. The retry wave arrives exactly when the server is least able to handle it — mid-recovery, often still working through the backlog from the original stumble, with less headroom than it had under normal load, not more. If the retry wave is enough to push the server back into failure, its response is identical: another burst of timeouts, another synchronized wave of retries a few seconds later, and now you have a self-sustaining oscillation where the server never gets a clean window to actually recover, because every attempt at recovery gets immediately hit by the next wave of retries generated by the last failure. The original transient blip, the thing that would have resolved itself in a couple of seconds with the traffic it was actually designed to carry, gets replaced by a standing failure that persists until someone intervenes, often by turning traffic off entirely and slowly turning it back on — the manual version of the thing the retry logic should have been doing automatically.

## Multiplying across a call chain

The picture gets meaningfully worse once you stop thinking about a single client and a single server, and start thinking about a realistic service architecture, where a request from a user passes through several layers before it's actually served — a gateway calls a frontend service, which calls a backend service, which calls a database or another downstream dependency. If each layer in that chain independently retries on failure, a single failure deep in the chain doesn't produce one retry. It produces a multiplication.

Say the database is struggling and occasionally times out. The backend service, calling the database, retries a failed call up to three times before giving up. The frontend service, calling the backend, also retries up to three times if the backend call fails. The gateway, calling the frontend, does the same. A single slow response from the database can now, in the worst case, result in the database receiving up to twenty-seven attempts stemming from one original user request — three retries at the outer layer, each one triggering up to three retries at the layer below, each of those triggering up to three retries at the layer below that. The struggling component at the bottom of the chain, the one component in the whole system with the least spare capacity at that exact moment, is the one that gets amplified traffic instead of relief. This is why "just add a retry, it's more resilient" is a genuinely dangerous default at any individual layer of a multi-hop system — resilience at one layer, evaluated in isolation, can be the exact thing that removes resilience from the system as a whole.

## Desynchronizing and disengaging

The fix for the thundering herd problem is conceptually simple: stop every client from retrying at the same fixed interval, and stop every client from retrying immediately. Exponential backoff addresses the second part — instead of retrying at a fixed one-second interval, wait one second, then two, then four, then eight, backing off further with each successive failure, so that a client hammering a genuinely broken dependency does so less and less frequently over time rather than at a constant rate. Jitter addresses the first part — instead of every client waiting exactly the computed backoff interval, each client adds a small randomized offset to it, so that ten thousand clients that failed at the same instant don't retry at the same instant a second time. Backoff reduces how hard the herd hits. Jitter breaks up the herd into a spread-out trickle instead of a synchronized wave. Together, they turn what would have been a single sharp spike of retry traffic into something closer to a smooth, gradually declining tail, which is a shape a recovering server can actually absorb.

Circuit breakers solve a related but distinct problem: at some point, retrying more cleverly is still retrying, and if a dependency is genuinely down rather than just slow, no amount of well-jittered backoff changes the fact that every attempt is wasted work that still costs the failing dependency a connection, a thread, or a unit of load it doesn't have to spare. A circuit breaker tracks the failure rate of calls to a dependency, and once that rate crosses a threshold, it stops making the calls at all for a cooldown period, failing immediately and cheaply on the calling side instead of waiting for a timeout on every single attempt. It's the difference between hitting a broken door softer and less often, versus simply not touching the door for thirty seconds and letting whoever's on the other side fix the lock. Only after the cooldown does the circuit breaker allow a small number of test requests through, to check — carefully, not with the full retry volume — whether the dependency has actually recovered before opening the floodgates back up.

## The generalizable lesson

The failure mode underneath all of this isn't really about retries specifically — it's about what happens when independent actors, each individually behaving reasonably, end up synchronized by a shared external event and converge on a scarce resource at the same moment. Retry storms are the most common instance of this in backend systems, but the same shape shows up in cache stampedes, where every client's cached value expires at the same computed time and they all recompute simultaneously; in connection pool exhaustion during a traffic spike; in autoscalers that all scale up in response to the same load metric and then all scale down together once it passes, overshooting in both directions. Whenever you're designing a mechanism meant to react to failure or change, ask not just "does this help one client recover" but "what does this mechanism do when every client is triggered by the same event at the same time" — because in a system with enough clients, that scenario isn't a rare edge case. It's the normal way outages actually happen.
