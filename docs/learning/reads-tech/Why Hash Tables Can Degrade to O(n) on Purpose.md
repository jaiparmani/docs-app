# Why Hash Tables Can Degrade to O(n) on Purpose

<small>6 min read</small>

Every introductory data structures course teaches the same fact about hash tables: lookup, insert, and delete are all O(1) on average. Most engineers absorb that as close to a guarantee and move on, and for the vast majority of code, treating it that way is harmless. The quiet asterisk on the claim is the word "average" — averaged over what distribution of inputs, exactly? For code running against your own test data, or ordinary user input, the average case is essentially always the case. For code running against input an adversary gets to choose — form field names, JSON keys, HTTP headers, anything an attacker can put bytes into before your server hashes it — the average case is no longer the relevant case, and the O(1) guarantee quietly stops applying to the thing it was supposedly guaranteeing.

## What a hash table is actually promising

A hash table maps a key to a bucket by running the key through a hash function and reducing the result to an index into an array. When two different keys land in the same bucket — a collision — the table has to store both, typically either by chaining them in a small linked list off that bucket or by probing forward to another open slot. The O(1) average case rests entirely on collisions being rare and roughly evenly spread across buckets, which in turn rests on the hash function scattering realistic inputs close to uniformly.

That assumption holds beautifully when the inputs are whatever your application naturally produces. It falls apart the moment someone can choose input specifically designed to collide, because the hash functions historically used for strings in most languages were fully deterministic: the same algorithm, with no randomness, running the same way on every request, every process, every server, forever. A deterministic function that's public knowledge — and language runtimes are open source, so it always was — can be inverted offline. Given enough time, an attacker can compute, once, a large set of distinct strings that all hash to the same value under that specific algorithm, entirely independent of any target server; the collision is a property of the algorithm, not of anything the server did.

## Turning that into a denial of service

Once an attacker has such a set, the attack is simple: submit a request whose parameters — POST form fields, JSON object keys, whatever the server parses into a hash map keyed by attacker-supplied names — are drawn entirely from that colliding set. The server, trying to build what it assumes will be a well-behaved hash map, instead ends up inserting every one of those keys into the same bucket. Chaining degrades to appending onto one long linked list, and each new insert has to walk the existing chain to check for a duplicate key before appending, which means inserting n colliding keys costs O(n) work per insert and O(n²) work in total. A request body of a few hundred kilobytes, built entirely from precomputed colliding strings, could keep a CPU core busy for seconds to minutes — no need for volumetric traffic, no botnet, just one crafted request doing algorithmically amplified damage.

This class of attack — algorithmic complexity attacks, sometimes just called hash flooding — had been described academically for years, notably by Scott Crosby and Dan Wallach in 2003, but it reentered public attention forcefully at the Chaos Communication Congress in late 2011, when researchers Alexander Klink and Julian Wälde demonstrated it working live against the hash implementations underlying PHP, Java, Python, Ruby, and other mainstream web-facing runtimes of the time — essentially the entire population of frameworks that parsed request parameters into a hash map without any defense against chosen-key collisions. The disclosure forced a wave of patches across languages that had, until then, treated their hash function's determinism as an implementation detail rather than a security boundary.

## Why randomizing the seed actually fixes it

The fix that stuck across languages was to seed the hash function with a random value generated once when the process starts, so the mapping from a given key to a given bucket differs unpredictably from run to run and machine to machine. The hash function itself often changed too — Python and Ruby, among others, adopted SipHash, a hash function specifically designed to behave like a keyed pseudorandom function: fast enough for everyday hashing, but resistant to exactly this kind of attack, because without knowing the secret key, an attacker cannot predict which inputs will collide.

The mechanism of the fix maps precisely onto the mechanism of the attack. The attacker's entire strategy depends on precomputing collisions offline against a known, fixed algorithm. A random per-process seed means there is no longer a single fixed algorithm to precompute against — the attacker would need to know the seed a specific server generated at startup, which is not exposed anywhere and changes every time the process restarts. The set of colliding strings computed against yesterday's seed, or against a different server's seed, is just an ordinary set of strings against today's — no more likely to collide than any other input. The fix doesn't make collisions impossible; it makes them unpredictable to anyone who isn't the server itself, which is all that's actually required.

## The lesson that outlives this specific bug

Big-O analysis describes what happens for typical inputs, and "typical" is doing a lot of unstated work in that sentence — it usually means inputs drawn from your test suite or your real users, both of which are, from a security standpoint, friendly distributions. The moment an adversary can choose the input, "typical" is no longer a safe assumption, because the adversary isn't sampling from your distribution; they're searching for the specific point in the input space where your data structure's worst case lives, and unlike your users, they have every incentive to find it and no reason to avoid it.

This applies well beyond hash tables. Any structure whose good performance depends on statistical assumptions about its input — a binary search tree that degrades to a linked list under sorted input, a cache whose eviction policy an attacker can game by predicting what it'll evict next, a load balancer whose hashing scheme routes all attacker traffic to the same backend — deserves the same question: if someone hostile got to choose the input, what would they choose, and does the system still behave the way its complexity analysis promised? Randomization is such a common answer to that question because it removes the one thing an attacker actually needs to construct a worst case in advance: certainty about how the system will behave before they've sent a single byte.
