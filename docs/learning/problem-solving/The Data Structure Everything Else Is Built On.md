# The Data Structure Everything Else Is Built On

<small>6 min read</small>

If you had to delete one data structure from computing and accept the consequences, the hash table would be the most expensive thing to lose. Not the array, which is a hardware fact more than a design; not the tree, which is elegant and replaceable. The hash table. It is the substrate under database indexes, compiler symbol tables, caches, deduplication, set membership, object property lookup in every dynamic language, and the partitioning schemes that decide which machine owns which key. Most of the code you have written today performed dozens of hash lookups without you thinking about it once.

The idea is almost insultingly simple. You want to find a value by key, and arrays already give you constant-time access by integer index. So convert the key into an integer, take it modulo the array size, and look there. Everything hard about hash tables is a consequence of that one shortcut, because the conversion is many-to-one: you are compressing an unbounded key space into a bounded number of slots, and by pigeonhole, distinct keys will land in the same place.

## "Expected" Is Doing an Enormous Amount of Work

The advertised complexity is O(1) lookup, insertion, and deletion. The word that matters is the one usually mumbled: *expected*. Worst case is O(n), and the gap between those two is not academic — it is the seam along which real systems fail.

The expected bound holds when keys distribute roughly uniformly across buckets. If they all land in one bucket, a chained hash table degenerates into a linked list and every operation becomes a linear scan. Nothing about the data structure prevents this; it is prevented only by the hash function behaving well on the keys you actually receive. The distinction between *the average over random inputs* and *the average over random hash functions* is why serious treatments talk about universal hashing, where the hash is drawn from a family such that any two distinct keys collide with low probability no matter what an adversary chose — turning a hopeful assumption about your data into a guarantee about your algorithm.

## Two Ways to Handle a Collision, and What Each Costs

The first strategy, separate chaining, keeps a list per bucket and appends colliding entries. It is simple, it tolerates load factors above 1.0 without breaking, deletion is trivial, and performance degrades smoothly rather than falling off a cliff. Its weakness is memory layout: each chain node is a separate allocation somewhere else on the heap, so following a chain means dependent pointer chases that the prefetcher cannot anticipate, and every entry carries pointer overhead.

The second, open addressing, stores entries directly in the table and resolves collisions by probing for another slot — linearly, quadratically, or via a second hash. Everything lives in one contiguous block, so a probe sequence often stays within a cache line or two, and a lookup that examines three slots may cost barely more than one that examines one. That locality is why performance-conscious implementations tend to prefer it. The price is fragility under load. As the table fills, occupied slots merge into long runs — primary clustering — and the expected probe count for linear probing blows up as the load factor approaches 1, so open-addressed tables must stay comfortably below full. Deletion is awkward too: emptying a slot breaks probe sequences that pass through it, so implementations use tombstones or backward-shift deletion, both of which add bookkeeping.

## Load Factor, and the Insert That Takes Forever

Load factor — entries divided by slots — is the dial that governs the whole trade. High load means less memory and more collisions; low load means the opposite. Real implementations pick a threshold and grow when they cross it: Java's `HashMap` uses 0.75 by default, CPython's dict resizes when it becomes two-thirds full. Growing means allocating a table typically twice the size and rehashing every existing entry into it, because the bucket index depends on the table size.

That rehash is O(n), and it lands entirely on one unlucky insert. Amortised across all insertions, the cost is O(1) — the same doubling argument that covers dynamic array growth — but the insert that triggers a resize on a table holding ten million entries does ten million units of work while the caller waits. If you are measuring throughput this is invisible. If you are measuring tail latency, it is a spike large enough to show up on a dashboard, and it is precisely the kind of thing that turns a p99 into a support ticket. Systems that cannot tolerate it use incremental rehashing, keeping both tables alive and migrating a few buckets per operation, trading a slower steady state for a bounded worst case.

## The Hash Function Is a Security Boundary

A good hash function needs three properties: it should distribute keys uniformly across the output space, it should be fast enough that hashing does not dominate the lookup it enables, and it should exhibit avalanche behaviour — flipping one input bit should change roughly half the output bits, so that similar keys such as `user_1000` and `user_1001` land in unrelated buckets rather than adjacent ones.

Miss the first property with attacker-controlled keys and you have handed over a denial-of-service vector. This is hash flooding, and it is not hypothetical. Crosby and Wallach laid out algorithmic complexity attacks at USENIX Security in 2003, and in 2011 Klink and Wälde demonstrated at 28C3 that the flaw was still live across essentially every major web platform: form fields and query parameters become dictionary keys, an attacker computes thousands of strings that collide under the runtime's published hash function, and a single ordinary-looking POST body drives the server into quadratic behaviour. The fix was not a better data structure but an unpredictable one. Python enabled hash randomisation by default in 3.3 and later adopted SipHash for strings and bytes; Rust's default hasher is SipHash with a per-table random seed, which is exactly why it is slower than the fastest available hash and why swapping it out is an explicit opt-in. Java took a different route, converting an over-long bucket into a balanced tree so the degenerate case costs O(log n). Both are admissions of the same thing: **the average-case guarantee is only as trustworthy as your assumption that nobody is choosing the keys on purpose.**

Set that against what the structure buys. A join between a million-row table and a thousand-row table becomes a single pass after building a hash table on the smaller side, rather than a nested scan. A cache is a hash table with an eviction policy stapled on. A compiler resolves every identifier through one. Deduplication and Bloom filters descend from the same primitive, and consistent hashing — the thing that lets a distributed cache add a node without invalidating everything — is the same idea applied to machines instead of memory slots.

What all of this rests on is a bet: give up the worst-case guarantee that a balanced tree provides, and take a constant-time average instead. It is a strange bet on paper, and it is almost always the right one, because average case is what you experience a billion times a day and worst case is what you experience when something has already gone wrong. The engineers worth having are the ones who can name the exceptions — a hard-real-time deadline where an unbounded probe sequence is unacceptable, an ordered traversal where a tree was always the right structure, an endpoint where the keys arrive from strangers — because knowing exactly when your default is wrong is a different and rarer thing than knowing how to use it.
