    Why Big-O Lies to You¶

    6 min read

    Big-O notation is the first serious abstraction most engineers learn, and like most first abstractions it gets absorbed as a truth about the world rather than as a deliberately lossy summary of one. The notation is not wrong. It is exactly as correct as it claims to be, which is much narrower than the way it gets used. Big-O describes how the cost of an algorithm grows as the input size grows without bound. That is the whole claim. It says nothing about how fast your program runs on the input you actually have, and it was never designed to.

    The imprecision is intentional and it is load-bearing. When we say an algorithm is O(n log n), we are asserting that there exists some constant c and some input size n₀ beyond which the running time never exceeds c·n log n. Both of those quantifiers are escape hatches. The constant c can be a thousand. The threshold n₀ can be larger than any input you will ever see. Everything that happens below n₀ is, by definition, outside the claim. Big-O throws away constant factors, throws away lower-order terms, and — most consequentially — assumes that every elementary operation costs the same. An array index, a pointer dereference, a division, a virtual call, a cache miss: in the model, all of them are one unit. In the machine, they differ by three orders of magnitude.

    The Threshold Nobody Mentions¶

    The canonical demonstration is sorting. Insertion sort is O(n²) and quicksort is O(n log n), and every introductory treatment leaves you with the impression that quicksort is simply better. It is, eventually. But insertion sort's inner loop is close to the cheapest thing a CPU can do: compare two adjacent elements, shift one, move on. It touches memory in a perfectly linear pattern, it branches predictably on nearly-sorted data, and it has no recursion, no partitioning, no pivot selection, and no function call overhead. Quicksort pays for its better growth rate with a much heavier per-element constant. For an array of twelve integers, the O(n²) algorithm wins outright, not marginally.

    This is not a curiosity — it is baked into essentially every production sort you have ever called. Real implementations are hybrids. C++'s standard sort is typically introsort, which runs quicksort until partitions fall below a small size (commonly around sixteen elements) and finishes with insertion sort. Timsort, used for object sorting in Java and as Python's sort, builds its runs with binary insertion sort and merges only above a minimum run length in the tens of elements. The people who wrote the fastest sorting code in the world concluded that the asymptotically worse algorithm is the right tool below a threshold, and hardcoded that threshold. The asymptotic ranking and the practical ranking are different orderings, and they only converge past a size that nobody bothers to tell you.

    Every Memory Access Is Not One Operation¶

    The deeper distortion is that Big-O inherits a machine model from an era when it was roughly true. In the RAM model, memory is flat: reading address 4 and reading address 4,000,000 cost the same. On real hardware they emphatically do not. An L1 cache hit resolves in a few cycles; a trip to main memory costs on the order of a couple hundred. Treat those as illustrative orders of magnitude rather than measured figures, but the ratio is not subtle.

    This is why the linked list, the darling of every data structures course, is so often a disaster. A linked list gives you O(1) insertion at a known position; the array needs O(n) to shift elements. Yet iterating a vector of a million integers frequently beats iterating an equivalent linked list by a wide margin, because the array occupies contiguous memory. Hardware fetches a cache line — 64 bytes on typical x86-64, so sixteen 32-bit integers — every time you touch one element, and the prefetcher, seeing a linear stride, pulls the next lines in before you ask. Sixteen elements, one memory stall. The linked list scatters its nodes across the heap, so each node->next is a dependent load the prefetcher cannot anticipate and the out-of-order engine cannot hide, because the next address is unknown until the current load returns. The array does O(n) work with excellent locality; the list does O(1) work with terrible locality; the array wins. Big-O cannot see this, because in its model there is nothing to see.

    The same blindness produces "galactic" algorithms — asymptotically superior methods whose constants make them useless. Matrix multiplication is the standard example: the naive method is O(n³), Strassen's is roughly O(n^2.807) and is genuinely used at large sizes, and a series of theoretical results has pushed the exponent down to around 2.37. Those record-holding algorithms are not implemented in any library you will ever link against. Their crossover points are astronomically large; they are proofs, not code.

    Amortized Is a Statement About Averages, Not About Tuesdays¶

    Then there is amortization, which hides a different kind of lie. Appending to a dynamic array is O(1) amortized: the array doubles when full, and the cost of copying is spread across the appends that preceded it, so any sequence of n appends costs O(n) total. This is a true and useful statement about throughput. It is not a statement about any individual append. The append that triggers the resize on an array holding a million elements allocates fresh memory and copies a million elements. Amortized analysis says that is fine because you earned it. Your p99.9 latency says it is not.

    That distinction is the difference between a batch job and a trading system, between a compiler and an audio callback, between a service whose SLO is average response time and one whose SLO is tail latency. In the hard-real-time case the amortized bound is nearly worthless; you need a bound on the worst single operation, which is why such systems reach for preallocated buffers and incrementally-resized structures that never do a large amount of work at once. The same reasoning explains why garbage collectors are judged on pause time and not just on collection throughput.

    None of this means Big-O is a bad tool. It is an excellent tool for the question it answers: if my input gets ten times bigger, does my program get ten times slower, a hundred times slower, or fall over entirely? That question is the difference between a system that survives growth and one that quietly dies at scale, and no amount of micro-optimization substitutes for getting it right. But it is a question about a limit, and you do not live at the limit. You live at n equals forty, or n equals ten million with a working set that does or does not fit in L2, on a machine with branch predictors and prefetchers and a memory hierarchy that the notation was explicitly constructed to ignore.

    Which suggests the actual skill is not knowing complexity classes but knowing which regime you are standing in. Small n with a hot loop is a constant-factor and locality problem, and asymptotics are noise. Large n with unbounded growth is an asymptotics problem, and constant factors are noise. Tail-latency-sensitive work is a worst-case problem, and averages are a trap. Big-O does not tell you which of these you are in — that is the one thing it cannot do, and it is the thing the job actually requires.
